## Context

前端当前使用 React 19、Ant Design 6、React Router 和 ECharts。布局壳与各业务页面已经可用，但大量布局通过页面内联样式独立实现：页面标题、筛选、表格容器和新增入口缺少统一层级；订单页仍使用悬浮新增按钮；响应式策略主要停留在侧栏默认收起，宽表格在手机端没有业务化降级。

本次改造覆盖导航壳、订单、订单详情、数据分析和四个基础资料页面。系统服务 2–3 名高频桌面用户，因此桌面信息效率优先，同时保证平板与手机能完成核心查询和操作。现有 API、数据模型、权限、校验和业务流程均视为稳定约束。

## Goals / Non-Goals

**Goals:**

- 建立全系统统一的应用壳、页面层级、间距、颜色和交互状态。
- 提高桌面工作区利用率与主操作可发现性。
- 为平板和手机定义可测试的导航与数据呈现降级规则。
- 复用 Ant Design 主题和组件能力，减少页面级重复样式。
- 保持业务逻辑不变，并通过现有 E2E 与多视口检查防止回归。

**Non-Goals:**

- 不改变后端 API、数据库、共享 schema、认证或权限。
- 不增加新的业务功能、统计指标或数据字段。
- 不替换 Ant Design、ECharts 或路由方案。
- 不以像素级重写所有 Ant Design 控件为目标。
- 不在本次改造中处理现有规格中主题切换与当前亮色实现之间的历史差异。

## Decisions

### 1. 采用“轻量专业”的单一视觉系统

**视觉论点：** 以经典蓝为唯一强调色，在冷中性画布上使用克制边界、清晰字阶和紧凑数据密度，形成可靠、安静的操作工作区。

**内容计划：** 应用壳提供方向感；页面标题区说明当前任务并承载唯一主操作；筛选区缩小数据范围；数据区支持查看与次级操作；分页/状态区说明结果范围。

**交互论点：** 侧栏展开收起使用短促宽度过渡；页面和异步内容以轻微淡入呈现；行悬停、操作菜单和弹窗使用一致的反馈与焦点状态。动画必须尊重 `prefers-reduced-motion`。

选择该方向是因为它在三个已比较方案中能为千级历史数据和高频录入提供最高工作区利用率，同时保留明确品牌识别。未选择深色高密度方案，因为其导航视觉重量过高；未选择暖灰宽导航方案，因为其桌面信息承载量较低。

### 2. 以主题 token 和少量共享布局组件统一页面

在应用级 `ConfigProvider` 中定义品牌色、字体、背景、边框、圆角、阴影与控件高度 token；在全局 CSS 中只放跨组件规则、响应式规则和必要的 Ant Design 补充样式。提取职责单一的共享呈现组件：

- `PageHeader`：标题、说明、面包屑补充信息和主操作。
- `PageToolbar`：搜索、筛选、刷新和结果上下文。
- `ResponsiveDataView`：桌面/平板表格与手机摘要条目的切换边界。
- `RowActions`：查看、编辑、删除等次级操作菜单与可访问名称。

这些组件只接收展示数据和事件回调，不拥有业务请求或表单状态。各页面继续拥有获取、分页、校验和提交逻辑，从而降低迁移风险。

替代方案是只用 CSS 类机械统一现有页面；该方式改动较少，但无法统一页面结构和响应式数据语义，因此不采用。另一替代方案是建立完整设计系统包；对当前项目规模过度设计，也不采用。

### 3. 桌面窄侧栏，手机抽屉导航

- 桌面（≥1280px）：侧栏默认 64px 图标模式，可展开查看完整标签，用户选择持久化。
- 横屏平板与小桌面（≥992px）：保留窄侧栏和完整表格，确保主操作不被遮挡。
- 竖屏平板与手机（<992px）：侧栏退出正常布局流，由顶栏菜单按钮打开抽屉；列表降级为摘要条目并保留分页。

导航项继续来源于单一配置，桌面菜单和手机抽屉复用同一路由、选中状态和分组语义。收起/展开和抽屉触发器使用真实按钮并提供可访问名称。

### 4. 页面主操作进入标题区，数据操作收敛到行级菜单

每页只允许一个视觉上突出的主操作。列表新增按钮位于标题区右侧；搜索与筛选进入标题下方工具栏；查看、编辑、删除等次级操作放在行级操作区，删除保持二次确认。订单页现有 `FloatButton` 将被移除。

该结构比悬浮按钮更可发现，也避免悬浮控件在手机端覆盖分页或数据内容。

### 5. 响应式数据呈现按业务优先级降级

桌面和横屏平板显示完整表格；竖屏平板与手机将宽表格呈现为整行可点击的摘要条目，每项包含主标识、一个关键关联字段和一个状态或时间字段，并复用原分页。订单详情中的编辑型复杂表格在自身容器内水平滚动，操作区在手机端改为双列网格，避免撑宽主页面。

选择业务化降级而非给所有表格统一添加横向滚动，因为只滚动会隐藏上下文和操作入口；同时避免为每页创建完全不同的移动端实现。

### 6. 保留业务数据流，统一异步与错误状态

页面现有请求、分页、搜索防抖、表单校验和提交函数不迁移到新状态库。共享组件通过 props 接收 `loading`、`empty`、`error` 与重试回调。保存和删除期间禁用重复操作；请求失败继续使用现有 toast，并在数据区提供可恢复的失败状态。

### 7. 分层验证而非依赖截图单点判断

- 单元/组件层：验证页面标题与主操作、响应式分支、导航选中/持久化、可访问名称和重复提交防护。
- 构建层：运行 web lint、测试与 build。
- 业务回归层：运行现有 smoke E2E 和订单详情 E2E。
- 视觉层：在桌面、平板和手机视口检查登录后导航、代表性列表、订单详情与分析页；截图用于发现布局问题，但不替代行为断言。

## Risks / Trade-offs

- **[风险] Ant Design Table 在手机端与自定义摘要视图维护两套列映射。** → `ResponsiveDataView` 使用同一行数据与明确的摘要渲染器，页面仅声明移动端需要的三个关键字段。
- **[风险] 全局 token 调整影响弹窗或图表等未预期区域。** → 先建立 token 基线，再按页面分批迁移并运行代表性视口回归。
- **[风险] 侧栏默认行为变化与已持久化的旧值冲突。** → 继续兼容现有 localStorage key；只有无存储值时使用新断点默认值。
- **[风险] 页面共享组件抽象过度，难以表达订单详情等复杂场景。** → 共享组件只统一外壳和状态，不抽象业务列、表单字段或图表配置。
- **[取舍] 手机端优先保证核心查询和操作，不承诺与桌面相同的信息密度。** → 低优先级信息进入详情页或展开内容。

## Migration Plan

1. 建立主题 token、全局基础样式和共享页面组件，并用测试固定公共行为。
2. 改造 AppShell、SideNav 与 TopBar，验证桌面/平板/手机导航。
3. 以订单列表作为代表页面验证标题、工具栏、响应式数据视图和弹窗规范。
4. 迁移基础资料列表，再迁移订单详情与数据分析等复杂页面。
5. 运行 lint、测试、build、E2E 与多视口视觉检查，修复回归后提交 PR。

所有改动均为前端兼容性改造，不需要数据迁移。若出现重大回归，可按组件/页面提交顺序回退；后端与数据无需回滚。
